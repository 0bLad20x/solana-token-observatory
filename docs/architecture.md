# Architecture

## Current boundary

Version 0.1 performs exactly one transformation:

```text
Jupiter Tokens V2 response
    -> immutable raw observation
    -> typed snapshot
    -> PostgreSQL
```

## Time semantics

- `received_at` / `observed_at` is generated by this collector when the HTTP response arrives.
- `source_updated_at` is copied from Jupiter's optional `updatedAt` field.
- Neither timestamp is silently replaced by the other.
- Timeframe construction is intentionally deferred until real update behavior has been measured.

## Persistence semantics

Every received token object creates:

1. one row in `jupiter_raw_updates` containing the complete JSON payload;
2. one linked row in `jupiter_snapshots` containing typed, frequently queried fields.

Repeated payloads are retained. This allows the project to measure how often polling produces a
new source state before introducing deduplication or retention policies.

## Explicitly out of scope

- OHLC/timeframe aggregation;
- indicators and trading signals;
- Meteora or RPC data;
- lifecycle classification;
- automatic execution;
- TimescaleDB-specific features;
- Rust implementation.
